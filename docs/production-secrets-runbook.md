# Production Secrets Runbook

AP-0022 runtime configuration is fail closed. This runbook defines a separate OpenBao service on a private management subnet/VM; do not run it in the application Compose project or on either PostgreSQL host. `deploy/openbao/server.hcl.example` uses TLS and Raft on a dedicated encrypted volume. Bind only private addresses, install certificates from the approved PKI, allow port 8200 only from agent/operations subnets, and keep the cluster port private to OpenBao peers. Do not put root tokens in Compose, systemd arguments, environment files, images, logs, tests, or traces.

## Provision and identity

1. Install the pinned OpenBao release on at least three independent secret-service nodes for HA, configure Raft and TLS, initialize using the protected ceremony, and unseal with separately held recovery shares. Store no initialization output on application/database hosts.
2. Create independent namespaces/paths and policies for each environment and role: `production/application`, `production/audit`, `production/migration`, and corresponding staging paths. Production identities must have no staging, audit, migration, policy, auth, or operator capabilities. Database paths issue distinct dynamic roles with finite TTLs and revocation statements.
3. For Compose/VPS workloads use OpenBao Agent AppRole auto-auth with a one-use response-wrapped SecretID delivered through systemd credentials. The Agent role ID is not secret; the SecretID and renewable Agent token stay on the host, mode 0400. Do not mount the token into the container. Use the supplied restricted systemd units and tmpfiles directories. The unprivileged agent renders `/run/auto-parto/secrets/secrets.properties` mode 0440 on tmpfs, readable by app UID/GID 10001. Separate systemd path units trigger a root-owned, fixed operation to apply permissions and restart only the application unit after a complete render. Audit and migration run under separate host identities/agent configurations and separate directories. Agent units have no Docker socket or privilege escalation path.
4. Enable `auto-parto-app.service` only after installing its matching OpenBao Agent unit. The app unit requires and follows the application Agent, and its pre-start gate waits up to 120 seconds for a complete bundle with correct group/mode and required keys. If audit is enabled, install `auto-parto-app-audit.conf.example` as a systemd drop-in and enable the separate audit Agent; the same pre-start gate then requires the audit bundle too. Enable both secret-change path units so a bundle rendered after delayed Agent login starts/restarts the app only after the gate passes. The app unit is a oneshot without a restart policy; Compose is invoked only after the pre-start gate passes.
5. Configure finite AppRole SecretID TTL/use count, token TTL/max TTL and renewal. Monitor renewal failures; stop/revoke the workload lease before expiry when renewal fails. Revoke the old database/provider credential only after the new credential is rendered and the application reports readiness. The rendered file is temporary and must not be copied to persistent storage.
6. Render all enabled credentials into the external properties file. The prod profile imports it as a required file. It contains runtime PostgreSQL username/password, Redis password, S3 keys, JWT signing private key and verification-key JSON, and optional provider/audit keys when enabled. Missing files or properties fail startup. URLs, hosts, bucket names and feature flags may remain deployment configuration; credential values do not.

`docker-compose.prod.yml` is the app-container boundary only. PostgreSQL, Redis, OpenBao, audit PostgreSQL, migration jobs, and the public TLS edge are separately deployed private services. Attach the application only to its private backend network and the TLS origin network; never publish database, Redis, audit, or OpenBao ports publicly. The health check uses readiness.

## Backup, restore, and unseal

- Schedule encrypted OpenBao Raft snapshots to immutable storage in a separate account/failure domain. Back up TLS/PKI material and recovery-share custody records separately; never back up an unsealed root token.
- Test snapshot integrity and restore to an isolated recovery cluster at least quarterly. Restore Raft snapshot, install matching TLS identity, unseal with quorum recovery shares, verify policies and lease revocation, and record RPO/RTO and approvers. Do not point production clients at the recovery cluster until its service identity and ACLs are checked.
- On node loss, replace the node and rejoin via Raft. On quorum loss, restore the last verified snapshot, unseal with recovery shares, rotate operator credentials, reissue workload SecretIDs, and revoke leases from the lost cluster. Keep application startup blocked until TLS, policy boundary, and credential checks pass.

## Rotation and rollback

- Database/provider secret rotation: issue a new short lease/credential, render atomically, restart the app, wait for readiness and a dependency-authenticated probe, then revoke the old lease and prove old authentication fails. For rollback, issue a fresh credential under the previous role and deploy the prior immutable image; never reactivate an already revoked password.
- JWT uses RS256. Store PKCS#8 private key only in the application policy and publish public keys at `/.well-known/jwks.json`. Add the next public key before switching the active `kid`; keep prior public keys through the maximum token lifetime plus clock skew. Verify both keys during overlap, switch signer, then remove/revoke the old public key and prove old tokens fail. Roll back by selecting a newly provisioned key, never by restoring a revoked private key.
- OpenBao token renewal, template rendering, restart, and shutdown must be monitored. Agent shutdown revokes its token; emergency revocation uses the scoped role accessor from the protected operations host.

## Repeatable staging drills

Run `deploy/openbao/verify-staging.sh` with short-lived non-root staging test identities and TLS CA. It checks app/audit/migration cross-policy denial. Run `deploy/openbao/verify-staging-leases.sh` with a staging app token and isolated TLS PostgreSQL test database to issue two dynamic leases, validate both credentials, revoke the prior lease and prove its credential is rejected, then renew/revoke the workload token and prove access is denied. Both scripts retain no credential output and cleanup leases on exit. Also execute these tracked drills and retain sanitized output with the deployment record: missing secret prevents app readiness; rotate Redis and enabled provider credentials and reject old values; rotate JWT keys through overlap/revocation using the published JWKS; restore snapshot and unseal a clean isolated cluster; verify the old cluster token cannot access the restored service. These require a provisioned OpenBao staging service and are not represented as passed by repository tests.
