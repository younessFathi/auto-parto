# Auto-Parto Deployment Architecture

## Deployment Goals

The deployment must provide:

- PostgreSQL as the durable system of record.
- Redis for bounded, recoverable infrastructure data.
- SeaweedFS through its S3-compatible gateway for uploaded files.
- Horizontally scalable WebFlux application instances.
- Secure secret management.
- Observable application and infrastructure behavior.
- Health checks, graceful shutdown, backups, and recovery procedures.

## Recommended Production Topology

```text
                         Internet
                            |
                    TLS load balancer
                            |
                 WebFlux application instances
                /      |        |          \
               /       |        |           \
      Redis   SeaweedFS S3  App PostgreSQL  Audit PostgreSQL
    cache/queue image files  business DB     audit history
                         independent resources and backups

External integrations:
- Firebase Cloud Messaging
- Email provider
- OpenTelemetry collector
```

The application instances should remain stateless except for short-lived in-memory state. User sessions, pending work, device tokens, durable business data, and audit delivery must not depend on one particular application instance.

## Application PostgreSQL

Application PostgreSQL is the system of record for:

- Users and profiles
- Part requests, part listings, and offers
- Wallets and ledger entries
- Addresses
- OTP challenges
- File metadata
- Notification records that require durable business history
- Audit outbox records required to recover asynchronous audit delivery

Production requirements:

- Initially run PostgreSQL on a dedicated VPS, isolated from the public Internet and from application containers.
- Later, move to a managed PostgreSQL service or highly available PostgreSQL cluster when availability requirements justify it.
- Enable encrypted connections and restrict network access to application instances.
- Run versioned schema migrations during deployment.
- Back up automatically and test restoration regularly.
- Monitor connections, replication lag, locks, slow queries, storage, and transaction failures.
- Use connection pooling appropriate for R2DBC and the database size.
- Do not expose PostgreSQL directly to the public Internet.
- Allow access only through a private network or a firewall allowlist of application hosts.
- Configure off-VPS encrypted backups so loss of the VPS does not lose the database.

Before production, define measurable recovery objectives. As an initial planning baseline, target an RPO of 15 minutes or better and an RTO of 2 hours or better, then confirm these values with product and operations. Use WAL archiving and point-in-time recovery for financial records, retain encrypted off-VPS backups, and test restoration in an isolated environment. Restore acceptance includes reconciling wallet balances against immutable ledger entries.

## Dedicated Audit PostgreSQL

Audit PostgreSQL is a separate production resource from Application PostgreSQL. It has independent compute, storage, connection pools, credentials, backups, monitoring, retention, and failure boundaries.

Audit PostgreSQL stores high-volume historical audit events exported from the application outbox. It is not the source of truth for users, ownership, offers, wallet balances, wallet ledger entries, or workflow state.

Production requirements:

- Use a separate PostgreSQL instance or managed database resource; a separate schema on the application instance is not sufficient for production isolation.
- Allow network access only from the bounded audit publisher and authorized audit-reader services.
- Use separate publisher and read-only credentials. The application runtime must not have delete or update privileges on audit history.
- Enforce a unique constraint on stable audit `event_id` values for idempotent retries.
- Partition audit events by time and index event time, event type, actor, subject, and correlation ID.
- Encrypt connections and storage, and keep audit backups independent from application backups.
- Define hot retention, archival retention, legal holds, redaction/deletion approvals, and immutable archival behavior.
- Monitor ingestion lag, failed writes, retry age, dead letters, storage growth, partition health, and backup/restore status.
- Test restoration and replay from Application PostgreSQL outbox rows and immutable audit archives.

Audit delivery is asynchronous and at-least-once. An audit database outage must not make ordinary business requests fail after the application transaction and its outbox row commit. Outbox backlog, delivery lag, and exhaustion state must be bounded and alerted.

## Identifier Strategy

Use two identifiers for persisted domain entities:

- Internal identifier: `BIGINT`/Java `long`, generated by PostgreSQL and used for joins and foreign keys.
- External identifier: UUID, generated by the application or database and exposed through APIs, URLs, logs, and events.

Example:

```text
users.id         BIGINT PRIMARY KEY
users.public_id  UUID NOT NULL UNIQUE
sellers.user_id  BIGINT NOT NULL REFERENCES users(id)
```

Rules:

- Never expose internal numeric IDs in public API responses or URLs.
- Use internal numeric IDs for efficient joins and compact indexes.
- Use UUIDs for public resource references and event IDs. Trace/correlation IDs belong to observability context. Idempotency keys are stable command keys supplied by the caller and scoped to the authenticated owner and operation.
- Add a unique constraint to every external UUID.
- Do not derive authorization from either identifier; authorization comes from the authenticated principal and ownership query.
- Keep identifier mapping inside the repository or application service boundary.

Store an idempotency request fingerprint for a defined retention period. Reusing a key with a different fingerprint returns `409 Conflict`; retrying the same command returns the original result where supported.

This provides efficient internal relational storage without making public identifiers predictable.

## Redis Persistence and Durability

Redis should not be the source of truth for wallets, offers, users, or ledger history. PostgreSQL owns durable business data.

Redis may contain:

- Cache entries
- Rate-limit counters
- Device-token indexes
- Pending notifications
- Retry jobs
- Short-lived locks or leases

Device-token records are authoritative in PostgreSQL because notifications must survive Redis loss. Store the owner, provider token, platform, status, creation time, last-seen time, and invalidation time. Registration is idempotent and enforces token uniqueness without allowing one user to claim another user's token. Redis contains rebuildable token indexes only.

Classify each Redis key before implementation:

### Disposable data

Examples: cache entries and rate-limit counters.

- Data can be recreated or naturally expires.
- Loss is acceptable.
- Use TTLs and memory eviction policies.

### Reconstructible notification projections

Examples: pending notification projections, fan-out streams, and retry scheduling hints.

- PostgreSQL outbox rows remain authoritative. Redis data in this category must be rebuildable from PostgreSQL and is not the only copy of recoverable work.
- Redis persistence may reduce recovery time, but AOF is not a correctness requirement for these projections.
- Use bounded queue sizes and explicit TTLs.
- Rebuild projections and reschedule due jobs from PostgreSQL when Redis data is lost or evicted.
- Use idempotency keys and leases so multiple instances do not process one job twice.
- Send exhausted jobs to a bounded dead-letter queue.

### Important business events

Do not store these only in Redis. Persist them in PostgreSQL first. Redis may be used as a delivery or processing projection.

For reliable notification creation, prefer this flow:

```text
Database transaction:
  save business change
  save outbox event

Outbox worker:
  claim event
  publish/send notification
  mark delivered or retryable
```

This avoids losing a notification between a PostgreSQL update and a Redis enqueue.

Outbox workers must claim work atomically with a lease, for example with a guarded update or `FOR UPDATE SKIP LOCKED`. A claim has an expiry so crashed workers can be recovered. Processing is at-least-once: delivery can succeed before the database marks the row complete, so consumers and providers must tolerate duplicates. Retry attempts, backoff, poison events, dead-letter retention, replay authorization, and ordering requirements must be bounded and observable.

For production, prefer a managed Redis service or a Redis HA deployment with:

- Authentication and TLS
- Persistence enabled when useful for faster projection recovery
- Replication and automatic failover
- Memory limits and eviction policy
- Monitoring and backup policy

Redis persistence improves recovery, but it does not replace PostgreSQL transactions or an outbox pattern.

## File Storage: SeaweedFS S3 Gateway

Use an S3-compatible storage abstraction in the application. Store only file metadata and object keys in PostgreSQL. The initial self-hosted provider is SeaweedFS, accessed through its S3 gateway.

```text
PostgreSQL:
  file id, owner id, request/listing id, object key, content type, size, checksum, status

Object storage:
  image bytes and generated variants
```

Use explicit file states:

1. Authenticate the caller.
2. Authorize ownership of the target request or listing.
3. Create a PostgreSQL metadata row in `PENDING` state.
4. Issue the staged upload destination or accept bytes.
5. Validate size, media type, content signature, checksum, and object existence.
6. Idempotently finalize the object and metadata as `ACTIVE`.
7. Mark failed or deleted objects as `TOMBSTONED` and delete them asynchronously.

Bounded reconciliation jobs find orphaned objects and metadata rows whose objects are missing. PostgreSQL and SeaweedFS are not treated as one atomic transaction.

### SeaweedFS

SeaweedFS is appropriate for the initial self-hosted deployment because it provides an S3-compatible gateway and can scale from a single-node development setup to a multi-node storage deployment.

Production requirements:

- Do not expose the S3 gateway publicly without TLS and an access policy.
- Configure persistent volumes and replication appropriate to the required durability.
- Configure explicit IAM policies with default-deny behavior.
- Persist IAM policy configuration instead of relying on in-memory defaults.
- Enable server-side encryption and store encryption keys in the secrets system.
- Test volume failure, restore, object deletion, and backup recovery.
- Keep the application behind the storage abstraction so migration to AWS S3 remains possible.

SeaweedFS is an infrastructure system that the team must operate. Its availability, replication, upgrades, and backups are the team's responsibility.

Recovery must include volume data, filer metadata, IAM policy state, encryption keys, object version/deletion policy, failure-domain placement, and restore order. Replication improves availability but is not a backup. Run bounded orphan and missing-object reconciliation after recovery.

### AWS S3

Best choice later if the application moves to AWS or if managed durability and lower operational work become more important than self-hosting.

Advantages:

- Highly durable and available
- Managed scaling
- Lifecycle policies
- Versioning and object locking
- IAM integration
- Presigned upload and download URLs
- No storage cluster to operate

Costs and considerations:

- Storage, request, and data-transfer costs
- Vendor dependency
- Region and compliance decisions
- Careful IAM and bucket policy design

### Recommendation

- Local development and automated tests: SeaweedFS or a filesystem test adapter.
- Initial self-hosted deployment: SeaweedFS S3 gateway.
- AWS production later: AWS S3.
- Keep the application dependent on an internal `FileStorage` port, not directly on a provider SDK.

Never use local container filesystem storage as the production source for user uploads.

## Application Deployment

Run multiple stateless application instances behind a TLS-terminating load balancer.

Each instance needs:

- Non-root container execution
- CPU and memory limits
- Readiness and liveness checks
- Graceful shutdown
- Configured connection and executor limits
- No committed secrets
- Structured logs to standard output

SSE requires additional deployment settings:

- Long idle timeouts at the load balancer
- Heartbeats enabled
- Per-user and global connection limits
- A documented multi-instance connection strategy
- Shared cross-instance notification fan-out, initially Redis Streams or an equivalent broker
- Sticky routing only as an optimization, never as the delivery mechanism

## Secrets and Configuration

Use a secret manager or protected deployment variables for:

- PostgreSQL credentials
- Audit PostgreSQL credentials
- Redis credentials
- JWT signing keys
- OAuth client secrets
- Firebase credentials
- Email provider keys
- Object-storage credentials

Configuration should be separated by profile:

- `local`: safe local defaults and optional dependencies
- `test`: fake providers and isolated containers
- `prod`: required external secrets with startup validation

Runtime application-database access uses R2DBC. Audit publishing uses a bounded non-blocking client or isolated bounded scheduler when the driver is blocking. Application and audit schema migrations use separate restricted JDBC migration jobs, run in deployment order before the corresponding workers and application rollout. Use expand-contract migrations when application versions overlap.

The development PostgreSQL migration job and fail-stop procedure are documented in [`postgresql-development-cutover.md`](postgresql-development-cutover.md). The audit PostgreSQL service is intentionally supplied through `docker-compose.audit.yml`, so an application-only PostgreSQL command does not require audit credentials. It is not yet an application cutover: MongoDB remains authoritative for business repositories until their PostgreSQL implementations and reconciliation fixtures pass.

Applications must fail safely when required production secrets are missing. They must not silently use development credentials.

### OpenBao

OpenBao is a suitable self-hosted secret-management choice for this project. It can store encrypted KV secrets, issue dynamic database credentials, manage leases, and support revocation.

Recommended usage:

- Store PostgreSQL, Redis, Firebase, OAuth, email, SeaweedFS, and JWT configuration secrets in OpenBao.
- Use separate policies and paths for local, test, staging, and production.
- Use dynamic PostgreSQL credentials where practical.
- Use OpenBao Transit or an external KMS for key operations when required.
- Authenticate workloads with short-lived machine identity, not a permanent root token.
- Keep OpenBao unexposed to the public Internet and protect it with TLS.
- Back up and test the OpenBao storage and unseal/recovery process.

OpenBao is not free operationally. A single OpenBao instance on the same PostgreSQL VPS creates a shared failure and compromise boundary. Initially use a separate small protected host or a managed secret service if available. If OpenBao is deployed on one node, document that it is a temporary availability risk and protect its recovery keys separately.

For JWTs, prefer asymmetric signing and key rotation with a published verification key set when possible. Do not put a long-lived root credential in the application container.

Prefer asynchronous clients for Firebase, email, OpenBao, and object storage. If a blocking SDK is unavoidable, isolate it on a bounded scheduler with explicit thread count, queue size, concurrency, timeout, cancellation, and shutdown behavior.

## Load Balancer and TLS Entry Point

For the initial deployment, use Caddy as the public TLS reverse proxy and load-balancer entry point when the number of application instances is small. Caddy provides automatic certificate management, simple configuration, health checks, and HTTP reverse proxying.

Use HAProxy instead when the team needs advanced L4/L7 traffic control, high connection volume, detailed health-check policy, or a dedicated load-balancer operating model. Use Traefik when service discovery and Docker labels are a primary requirement.

Initial recommendation:

```text
Internet -> Caddy (TLS) -> WebFlux application instances
                         -> SeaweedFS only through a private/admin route
```

Rules:

- Terminate TLS at the edge and use secure internal transport where network trust is not absolute.
- Forward and validate `X-Forwarded-*` headers only from trusted proxy addresses.
- Configure long idle/read timeouts for SSE.
- Configure active health checks and remove unhealthy instances.
- Rate-limit authentication and upload endpoints at the edge as an additional layer.
- Do not expose PostgreSQL or Redis through the public load balancer.

Application rate-limit failure policy is endpoint-specific: OTP, login, token registration, and notification abuse controls fail closed or use a bounded local fallback when Redis is unavailable. Ordinary reads may use a documented degraded policy. Edge rate limiting is defense in depth.

## CloudEvents Decision

CloudEvents is not a logging format. Logs should use structured JSON and OpenTelemetry correlation with trace and span IDs.

Do not add CloudEvents only to standard application logs. For the current project, it is optional rather than required.

Use CloudEvents later for durable business or integration events such as:

- `part_request.created`
- `part_listing.created`
- `offer.created`
- `offer.accepted`
- `wallet.credited`
- `notification.requested`

If introduced, publish CloudEvents from a PostgreSQL outbox after the business transaction commits. Include a UUID event ID, event type, source, subject, time, schema version, and correlation/trace ID. Consumers must be idempotent.

For the current scope, an internal versioned event DTO plus an outbox is enough. Add CloudEvents when a second service, external consumer, webhook, or event broker needs a stable interoperability contract.

## Observability Solution

Use the OpenTelemetry and Prometheus ecosystems together:

```text
Application
  |-- Micrometer metrics --------> Prometheus ----> Grafana
  |-- OpenTelemetry traces ------> Collector -----> Tempo or Jaeger
  |-- Structured JSON logs ------> Loki or ELK ----> Grafana/Kibana
  |
  +-- correlation_id / trace_id shared across all signals
```

### Metrics

Use Micrometer in Spring Boot and expose Prometheus metrics.

Track:

- Request count, latency, status code, and error rate by route
- WebFlux event-loop and executor saturation
- PostgreSQL connection pool usage and query latency
- Redis command latency, memory, evictions, and errors
- Cache hit and miss rates
- Wallet operation count and failure count
- Notification success, failure, retry, and dead-letter counts
- Pending queue depth and oldest queued item age
- FCM response latency and invalid-token count
- Active SSE connections and rejected connections
- File upload count, size, failure, and storage latency

Do not use unbounded user IDs, email addresses, tokens, or notification IDs as metric labels. High-cardinality labels can exhaust the monitoring system.

### Distributed tracing

Use OpenTelemetry instrumentation for:

- Incoming WebFlux requests
- Outgoing HTTP calls to Firebase, email, and object storage
- PostgreSQL queries
- Redis commands where supported
- Background notification jobs

Every trace should carry a trace ID. Background jobs must preserve the originating trace context when possible and create a new linked span when not.

### Structured logs

Write JSON logs containing:

- Timestamp
- Log level
- Service name and version
- Environment
- Trace ID
- Span ID
- Correlation/request ID
- Safe operation name
- Outcome and duration

Never log:

- JWTs or private keys
- OTP values
- Passwords
- Firebase tokens
- Complete notification bodies
- Payment credentials
- Sensitive personal data

Use a centralized log system such as Loki/Grafana for a simpler deployment, or Elasticsearch/Logstash/Kibana when advanced search and enterprise operations require it.

Before production, define retention and access boundaries. A practical initial policy is short retention for debug logs, longer retention for audit/security events, sampled traces in production, and bounded metric retention sized to the monitoring budget. Observability systems contain sensitive operational data and require authentication, authorization, backups where required, and named alert owners with runbooks.

### Health checks

Expose separate checks:

- Liveness: the process is running and can respond.
- Readiness: the instance can accept traffic and required dependencies are available.
- Dependency health: PostgreSQL, Redis, Firebase, and object storage status, exposed as protected diagnostics.

Public liveness and readiness endpoints must not require a user JWT. Readiness includes only dependencies required for the routes served by that instance. Firebase, email, notification, and upload failures should support documented degraded behavior instead of automatically removing every API instance from service. Detailed dependency information should be protected or exposed only to the orchestrator and operations team.

### Alerting

Use Prometheus Alertmanager or the equivalent managed alerting service.

Alert on:

- High HTTP 5xx rate
- High request latency
- PostgreSQL connection exhaustion
- PostgreSQL storage or replication failure
- Redis memory pressure or failover
- Growing notification retry/dead-letter queues
- Oldest pending notification exceeding an SLA
- FCM failure or invalid-token spike
- Excessive authentication and OTP failures
- Rejected SSE connections
- File-storage failures
- Missing application heartbeats

Every alert should have an owner, severity, runbook link, and recovery objective.

## Recovery Requirements

The production operation must document:

- PostgreSQL backup and restore
- Redis recovery and queue replay
- Object-storage recovery
- Secret rotation
- Application rollback
- Database migration rollback or forward-fix strategy
- Notification duplicate handling after recovery
- Incident communication and ownership
