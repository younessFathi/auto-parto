# AP-0048 Admin-Protected Swagger and OpenAPI Documentation

- **Status:** Proposed
- **Type:** Technical Enhancement
- **Feature:** [Platform and Data](../features/F01-platform-and-data.md)
- **Linked Tickets:** [AP-0025 Safe API Error Contract](AP-0025-api-error-contract.md), [AP-0030 Application Boundaries](AP-0030-application-boundaries.md), [AP-0049 Domain OpenAPI YAML Design](AP-0049-design-domain-openapi-yaml.md), [AP-0021 TLS Entry Point](AP-0021-tls-entrypoint.md)
- **Source:** `docs/architecture.md` Authentication and Authorization; `docs/api-boundaries.md`

## Description

Provide an accurate Swagger UI and OpenAPI specification so administrators can inspect the application's current HTTP API. Restrict the UI, the generated specification, and any supporting Swagger resources to users authenticated with the existing application JWT and canonical `ROLE_ADMIN` principal. Authentication and role authorization must use the same security chain and canonical-principal rules as the rest of the API; do not create a separate Swagger password or authentication mechanism.

Swagger/OpenAPI is already on the classpath, but its paths are currently permitted anonymously and excluded from JWT processing. This ticket closes that access gap and completes application/browser/domain-group acceptance locally or in isolated staging, without waiting for Cloudflare. Accepted AP-0048 proof is a prerequisite to AP-0021 edge rollout; AP-0021 then establishes the edge and owns through-edge regression before public release. Admin documentation access does not grant business access: every API request retains its own role and ownership rules.

Keep OpenAPI documentation separate from controller implementation code. AP-0049's proposed design uses Java controller/API contract sources as the single source of truth and generates a separate YAML output for each domain. Put OpenAPI descriptions on small API contract interfaces implemented by controllers; do not hand-maintain parallel YAML contracts, add a large block of documentation annotations to controller methods, or create one catch-all interface. Keep runtime authorization and business behavior in the existing security/controller layers.

## Acceptance Criteria

1. Require a valid existing application JWT with canonical `ROLE_ADMIN` for `/swagger-ui/**`, `/swagger-ui.html`, `/v3/api-docs/**`, `/webjars/**`, and any configured alternate Swagger/OpenAPI path. Missing or invalid credentials receive the established 401 contract; authenticated non-admin roles receive 403; administrators can load both UI and specification.
2. Ensure Swagger requests are not bypassed by the JWT authentication filter or permitted by an earlier security matcher. Derive the role only from validated canonical authentication; never trust a request parameter, header, or OpenAPI UI input as an authorization claim.
3. Configure Swagger API calls with the existing bearer JWT scheme and `persistAuthorization: false`. Entered API tokens remain in page memory and are separate from the launcher documentation-admin token, which must never be automatically injected into non-document API/SSE calls. Preserve actual endpoint roles/ownership, including authenticated ACTIVE-file reads without an invented owner/role check; do not persist bearer credentials in browser storage.
4. Document canonical `/api/v1` routes and their actual DTOs, validation constraints, response/error contracts, and authentication requirements. Reconcile legacy aliases with `docs/api-boundaries.md`: mark supported aliases deprecated with their sunset, or exclude retired routes. Do not advertise removed routes or imply that documentation grants broader access.
5. Implement AP-0049's accepted design: keep controller mappings, DTOs, validation, and authorization as executable sources; put OpenAPI descriptions on small API contract interfaces implemented by their controllers; generate standalone YAML files under `target/generated-openapi/v1/<domain>.yaml` and expose matching protected domain groups in Swagger UI. Do not maintain a second hand-authored YAML source.
6. Keep the OpenAPI specification free of secrets, internal credentials, private deployment details, and sensitive example data. Avoid exposing actuator, migration, or internal-only operations as public API documentation; if intentionally documented for administrators, label their operational scope clearly.
7. Add focused security/controller integration coverage for anonymous, malformed/expired-token, authenticated non-admin, and administrator access to both the UI and every domain specification. Add contract coverage that confirms route groups and the bearer scheme remain aligned with the canonical API catalog and that the accepted source of truth appears correctly in each domain spec.
8. Implement and document the selected operator headed Playwright launcher in `docs/api-openapi-domain-design.md`: fresh nonpersistent context, blocked service workers, trusted exact HTTPS origin (explicit loopback HTTP only locally), same-origin packaged assets, no-echo in-memory admin JWT, and interception installed before canonical first navigation. Inject only GET/HEAD on the boundary-checked documentation allowlist; use `route.fetch({headers, maxRedirects: 0})` and fulfill only nonredirect responses, aborting all 3xx without following/forwarding them. Never use injected `route.continue({headers})`, global extra HTTP headers, cross-origin resources, or token persistence in URLs/arguments/environment/files/browser storage/diagnostics. On documentation 401/403 or close/Ctrl+C, stop injection and discard context/token references; relaunch with a new validated token. Direct browser navigation remains 401; no new app cookie/password/auth model. Save only explicitly selected safe YAML. Enabled profiles remain admin-protected; disabled profiles cannot fall back to anonymous access.
9. Complete application/security, fresh-browser launcher, all seven JSON/YAML groups and download acceptance locally or in isolated staging, independently of Cloudflare. Hand accepted proof to AP-0021, which establishes Cloudflare/origin routing and owns through-edge regression before public release; AP-0048 completion must not depend on that later edge deployment.

## Test Scenarios

1. **Given** an unauthenticated request, **when** it requests the Swagger UI, JSON specification, or supporting UI assets, **then** it receives the established 401 response and no specification content.
2. **Given** a valid buyer or seller JWT, **when** the user requests the UI or specification, **then** access is denied with 403 and no documentation body is returned.
3. **Given** an operator with a validated admin JWT entered only at the launcher no-echo prompt, **when** a fresh nonpersistent context first navigates to canonical Swagger HTML, **then** trusted same-origin assets/configuration, all seven JSON/YAML groups and an explicitly selected safe download succeed without redirects or token persistence.
4. **Given** the launcher supplies documentation credentials, **when** Swagger calls a same-origin protected business API without an explicitly entered API token, **then** it receives 401; an entered buyer/seller token follows its normal endpoint role/ownership rules, and the documentation token is never substituted. SSE requests retain normal streaming.
5. **Given** canonical and legacy route changes, **when** OpenAPI contract tests run, **then** documented routes match `docs/api-boundaries.md` and removed routes are absent.
6. **Given** Swagger is disabled by an explicit profile setting, **when** any Swagger/OpenAPI path is requested, **then** it is unavailable and cannot become public through a security matcher.
7. **Given** unrelated origins/paths, lookalike prefixes or any documentation 3xx redirect, **when** the launcher handles the request, **then** it blocks cross-origin resources, withholds credentials on non-document paths, aborts redirects without following/forwarding them, and leaks no token to a redirect target. Service workers cannot bypass the scoped interception.
8. **Given** documentation credentials expire or are malformed/non-admin, **when** documentation returns 401/403, **then** injection stops and context/token references are discarded; explicit close/Ctrl+C performs the same local logout without claiming global JWT revocation. A new validated JWT requires a fresh launch. Plain address-bar requests remain 401.
9. **Given** no Cloudflare edge has been deployed, **when** the application/group/browser checks pass locally or in isolated staging, **then** AP-0048 can complete and AP-0021 may start edge establishment; AP-0021 must separately pass through-edge regression before public release.

## Definition of Done

AP-0049's design is accepted and Swagger/OpenAPI accurately describes active domain groups, administrator-only wherever enabled. The selected local launcher and fresh-browser/token-isolation/redirect-refusal/cleanup acceptance pass locally or in isolated staging, as do application security, YAML/reference, route-catalog and applicable verification suites. Existing JWT, canonical role checks, safe errors and actual endpoint authorization remain intact. Local usage/profile behavior and safe YAML downloads are documented. Accepted application proof is handed to AP-0021; Cloudflare/origin deployment is not required for AP-0048 completion, and AP-0021 owns through-edge regression before public release.
